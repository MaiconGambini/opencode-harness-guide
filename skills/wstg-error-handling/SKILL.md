## Use this skill when

- Conducting penetration tests or security assessments targeting error handling
- Analyzing HTTP error responses, stack traces, memory dumps, or verbose error messages
- Identifying information disclosure through improperly handled exceptions
- Mapping internal services, frameworks, or APIs via error output
- Fuzzing inputs to trigger unhandled exceptions and observing server behavior
- Reviewing code or configurations for error handling weaknesses
- Auditing microservice architectures where inconsistent error handling leaks service identity

## Do not use this skill when

- The task involves general input validation testing (use WSTG-INPV)
- Testing authentication error messages for user enumeration (use WSTG-IDENT)
- Testing for SQL injection via error-based techniques (use WSTG-INPV-05)
- Reviewing non-web applications or protocols outside HTTP/HTTPS

## Overview

Error handling is a universal concern across web servers, application frameworks, databases, and microservices. Developers often design for the happy path and neglect how the system behaves under unexpected input. Improper error handling leaks internal implementation details, enabling attackers to:

- **Map internal APIs and frameworks**: Error messages often reveal the technology stack, library versions, and internal service names.
- **Discover integration points**: Microservice architectures that return distinct error formats per service expose the topology of backend systems.
- **Enumerate version information**: Stack traces and debug pages frequently include version strings of frameworks, language runtimes, and database engines.
- **Denial of service**: Unhandled exceptions can panic the runtime, deadlock threads, or exhaust resources.
- **Bypass controls**: Exceptions thrown outside the normal logic path may skip authorization checks or validation routines, granting unintended access.

Error handling failures appear as: stack traces, network timeouts, input mismatch errors, memory dumps, and database error messages. The underlying cause is the same across all forms: **failure to anticipate and safely handle invalid state**.

## Test Cases

### WSTG-ERRH-01: Testing for Improper Error Handling

**Objective**

Identify existing error output generated by the target system and analyze returned error content for sensitive information disclosure, internal system mapping, and exploitable misconfigurations.

**Why this matters**

Error messages are the primary weakness in mapping out systems. Every distinct error format, server banner, or stack trace line the application leaks is a piece of the puzzle an attacker assembles to understand the technology stack. Under microservice architectures, inconsistent error handling between services creates a fingerprintable map of the entire backend topology.

#### How to Test — Web Servers

Every web application runs on a web server (NGINX, Apache, IIS, or an embedded server). Web servers have well-known error message formats and behaviors that can be identified through documentation or by setting up reference instances locally.

Trigger error conditions at the web server layer:

- **Request non-existent resources**: Probe random files and directories that do not exist. Observe whether the server returns a default 404 page that reveals server type and version.
- **Request restricted resources**: Attempt access to known-existing directories (e.g., `/admin`, `/config`, `/backup`). Contrast behavior — does the server return 403, a blank page, directory listing, or redirect? Inconsistent responses indicate custom error handling vs. default server behavior.
- **Break the HTTP protocol**: Send malformed requests that violate RFC specifications. Examples include extremely long URL paths, invalid header formatting, unsupported HTTP versions, or malformed chunked encoding. Even when the application layer catches errors, the web server itself may respond with its own error page because it must handle the request before the application sees it.
- **Examine response headers**: Server headers (`Server`, `X-Powered-By`, `X-AspNet-Version`) are not error messages per se but are commonly exposed alongside error pages and reveal the stack.

**What to look for**

- Default web server error pages instead of customized application error pages
- Server version and OS information in error page footers or headers
- Directory listings on 403 responses (misconfigured permissions)
- Different error formats between the web server layer and application layer (indicates where the error originated)

#### How to Test — Applications

Applications are the most error-prone layer because they are custom-built, integrate with multiple backend services, and require developers to anticipate every failure path for every input.

Test methodology:

1. **Identify input points**: Catalog every location where the application accepts data — URL parameters, form fields, JSON/XML bodies, file uploads, cookies, custom headers, and WebSocket messages. Include indirect inputs such as `Referer` and `User-Agent` headers that may be logged or processed.

2. **Analyze expected input types**: For each input point, determine what the application expects — strings, integers, booleans, JSON objects, XML documents, file types, date formats, or enumerated values.

3. **Fuzz each input point with targeted payloads**: Fuzzing with random data is inefficient. Build focused payloads per input type:
   - **Type violations**: Send a string where an integer is expected, an array where an object is expected, or a boolean where a string is expected.
   - **Parser-breaking payloads**: For JSON, send unclosed brackets, duplicate keys, or deeply nested structures. For XML, send malformed entities, unclosed tags, or billion-laughs expansions.
   - **Boundary violations**: Send extremely long strings (10,000+ characters), empty values, null bytes, negative numbers where positive is expected, or values exceeding maximum ranges.
   - **Character set attacks**: Send special characters that are invalid for the expected data type — control characters, Unicode homoglyphs, path traversal sequences (`../`), or null bytes injected into filenames.
   - **CRLF injection**: Inject carriage-return and line-feed sequences in parameters that may be processed by intermediate servers or logged.
   - **Encoded payloads**: URL-encode, double-encode, or use Unicode encoding variants of the above to bypass input validation filters.

4. **Map error origins**: When an error occurs, determine which backend service produced it. Database errors look different from application server errors, which look different from proxy errors. A microservice architecture with inconsistent error handling will leak which service handles each request, enabling a focused attack per service.

**What to look for**

- **Stack traces**: Full call stacks revealing file paths, class names, method names, and line numbers. These expose internal code structure, library versions, and sometimes hardcoded credentials or connection strings.
- **Database error messages**: SQL syntax errors, constraint violation messages, or connection failure details that reveal the database engine, table names, column names, or query structure.
- **Framework debug pages**: Development-mode error pages from Django (yellow debug page), Rails (red error page), ASP.NET (yellow screen of death), Spring Boot (Whitelabel error page), or Express (default error handler).
- **Memory dumps**: Partial or full memory contents exposed in error output, which may contain session tokens, encryption keys, or user data.
- **Service-specific error formats**: JSON error objects with fields like `errorCode`, `serviceName`, `timestamp`, `stackTrace`, or `requestId` that include internal service identifiers.
- **Hidden errors in non-obvious places**: Errors returned in 302 redirect bodies, inside HTML comments, in JSON responses with HTTP 200 status, or in custom response headers.

**Efficiency tip**: Prioritize input points that interface with backend services (search boxes, file uploads, API endpoints, authentication forms). These are most likely to pass errors through from integrated systems.

### WSTG-ERRH-02: Testing for Stack Traces

> In WSTG v4.2, this test was merged into WSTG-ERRH-01. It is preserved here separately because stack trace detection requires specific technique beyond general error fuzzing.

**Objective**

Detect whether the application exposes stack traces — detailed debugging output showing the call hierarchy, file paths, and line numbers of code that executed up to the point of failure.

**Why this matters**

A stack trace is the single most information-dense error output an application can produce. A single trace can simultaneously expose: the programming language and version, the framework and its version, the internal directory structure of the deployment, class and method naming conventions, the exact line of code where an exception occurred, and sometimes parameter values or connection strings passed to the failing function. Stack traces eliminate guesswork for an attacker building targeted exploits.

#### How to Test

Stack traces are produced when an unhandled exception propagates to the top of the call stack. The application must be forced into an exception state that the framework or runtime does not catch.

Targeted techniques for triggering stack traces:

- **Type confusion**: Pass a string where an integer or date is expected in query parameters, form fields, or API bodies. Type coercion failures in strongly-typed languages produce detailed tracebacks showing the exact parsing location.
- **Null/invalid references**: Submit empty or null values for required parameters. If the application does not validate before dereferencing, a null-pointer/undefined-variable exception may propagate.
- **Resource exhaustion**: Trigger file-not-found exceptions by requesting paths with traversal sequences; trigger database connection failures by overwhelming connection pools; trigger timeout exceptions with extremely slow request bodies.
- **Deserialization failures**: Send malformed serialized objects (JSON with wrong structure, XML with missing required elements, binary formats with corrupt data). Deserializers often produce verbose stack traces when they cannot parse input.
- **Authentication/authorization edge cases**: Access protected endpoints without credentials, with expired tokens, or with tokens for a different role. Some frameworks throw authorization exceptions that include stack traces in development mode.
- **HTTP method violations**: Send POST to GET-only endpoints or vice versa, triggering method-not-allowed handlers that may leak traces.
- **Content-Type mismatches**: Send `application/xml` to an endpoint expecting `application/json`, or send binary data to a text parser.

**What to look for**

- Complete call stacks with file paths (e.g., `/var/www/app/controllers/user.py:42`, `C:\inetpub\wwwroot\app\auth.cs:117`)
- Framework-specific trace formats: Python traceback with `Traceback (most recent call last):`, Java stack trace with `at com.example...`, .NET stack trace with `at Namespace.Class.Method()`, Node.js stack trace with `at Object.<anonymous>`.
- Development-mode indicators: `DEBUG=True`, `ASP.NET` detailed error mode, `RACK_ENV=development`
- Version strings for language runtimes, frameworks, and libraries appearing in trace headers
- Parameter values or variable contents dumped into trace output by debug-level logging

**Common vulnerability pattern**: Applications deployed to production with debug/development mode enabled. This is the single most common cause of stack trace leakage. The framework's default error handler in development mode is designed to be verbose; if the deployment process does not explicitly set production mode and configure custom error pages, every unhandled exception becomes an information disclosure.

## Common Vulnerability Patterns and Misconfigurations

### Pattern 1: Production Debug Mode
The application is deployed with framework debug/development mode enabled. Every exception returns a full stack trace with file paths and variable dumps. This is the single highest-yield finding in this category because it requires no fuzzing — any unexpected input that reaches an uncaught exception triggers disclosure.

### Pattern 2: Default Server Error Pages
The web server (NGINX, Apache, IIS) serves its built-in error pages rather than custom application-defined pages. These default pages include server name, version, and sometimes OS information in their footers or headers.

### Pattern 3: Inconsistent Microservice Error Formats
Each backend service returns errors in its own format — one returns JSON with `{error, service, traceId}`, another returns XML with `<fault>`, a third returns a plain-text stack trace. An attacker can enumerate all services in the architecture by triggering errors at different endpoints and fingerprinting the response format.

### Pattern 4: Database Error Passthrough
Database errors (constraint violations, syntax errors, connection failures) are returned directly to the client without sanitization. These reveal: DBMS type and version, table names, column names, query structure, and sometimes data from adjacent rows.

### Pattern 5: Error in Success Clothing
The HTTP response code is 200 or 302, but the response body contains an error message, stack trace, or exception details. Automated scanners that only check response codes miss these entirely. Manual inspection of response bodies on unexpected input is essential.

### Pattern 6: Verbose 404/403 Pages
Custom 404 or 403 pages reveal the application's directory structure ("The file /admin/users/secret.txt was not found" vs. "File not found"), enabling path traversal and forced browsing.

### Pattern 7: Input Reflection in Errors
User-supplied input is reflected in error messages without sanitization. This enables reflected XSS through error pages and, in some cases, template injection if error messages are rendered through a template engine.

### Bug-Finding Efficiency Tips

- **Start with the HTTP layer before the application layer**: Web server errors are faster to trigger and require no input analysis. Break the HTTP protocol in the first 5 minutes of testing.
- **Map error variety before depth**: Hit every endpoint once with a clearly invalid input (e.g., a single quote) to see how many distinct error formats exist. Each distinct format is a different service or error handler to investigate.
- **Target parsers and deserializers**: JSON parsers, XML parsers, file upload handlers, and date parsers are the most likely components to produce verbose errors because they perform complex type coercion and format validation.
- **Trace error differences to map architecture**: If `/api/users` returns a JSON error and `/api/orders` returns an XML error, you have identified two different backend services. Treat each as a separate attack surface.
- **Check non-200 responses manually**: Always inspect the response body of 301, 302, 400, 403, 404, 405, 500, 502, and 503 responses. Frameworks often return errors in redirect or error-status bodies.
- **Use boundary values, not random data**: Sending `-1`, `0`, `9999999999`, empty string, and `null` is more likely to trigger errors than random strings because these hit edge cases in validation logic and numeric overflow checks.

## Remediation Guidance

### For WSTG-ERRH-01 (Improper Error Handling)

- **Implement a global error handler**: Catch all unhandled exceptions at the application's outermost boundary and return a generic error response. No stack trace, no file path, no database error, no service identifier.
- **Configure custom error pages at the web server level**: Override default 404, 403, and 500 error pages on NGINX, Apache, or IIS with generic, branded pages that reveal nothing about the server.
- **Use a consistent error format across all services**: In microservice architectures, define a standard error response schema and enforce it at every service boundary. Every service returns the same structure, preventing service fingerprinting.
- **Log detailed errors server-side only**: Send the full error details (stack trace, request context, internal state) to a server-side logging system. The client receives only a generic message and a correlation ID for support reference.
- **Disable debug mode in production**: Verify that `DEBUG=False`, `ASPNETCORE_ENVIRONMENT=Production`, `NODE_ENV=production`, `RACK_ENV=production`, or equivalent is set in every deployment environment.
- **Validate and sanitize before processing**: Validate input types, ranges, and formats before passing data to backend services. Invalid input should be rejected early with a controlled, non-revealing error message.
- **Review OWASP Proactive Controls C10**: Handle All Errors and Exceptions, and the OWASP Error Handling Cheat Sheet for language-specific implementation patterns.

### For WSTG-ERRH-02 (Stack Traces)

- **Never render stack traces to the client**: This is non-negotiable. In production, stack traces go to logs, never to HTTP responses.
- **Configure framework-level production error handlers**: Every major framework provides a production error mode. Django: set `DEBUG=False` and configure `handler500`. Rails: set `consider_all_requests_local = false`. Express: set `NODE_ENV=production` and register a final error-handling middleware. ASP.NET: use `app.UseExceptionHandler()` with a generic error page in production.
- **Test error pages in a staging environment**: Before deploying, intentionally trigger exceptions against staging and verify that the response contains no trace information.
- **Add a security regression test**: Include a test in the CI/CD pipeline that sends malformed requests to each endpoint and asserts that the response body contains no stack trace indicators (file paths, line numbers, framework trace patterns).
