# Harness v1.3 — Context for Future Agents

Read this before changing the findings contract, the learned-rules ledger, the Refine phase, the
adherence adapter, the `rule-verifier`, any permission block in `opencode.jsonc`, or the rule
injection in `agent/spec-lead.md`. It captures what v1.2 left unrecorded, what v1.3 changed, and the
invariants you must not break.

Read `v1.2-context.md` first — its fifteen invariants all still hold, and it is the correct account of
the gate's fail-closed machinery this layer builds on.

## TL;DR

v1.2 made **verification numeric**. v1.3 makes **instruction-following recorded**: which written rule
was broken, in which lane, whether the reviewer can cite a rule at all, and how much of the rulebook a
program checks — and hands a recurring break to the next lane at dispatch time. The old prose
write-back is dead; a typed record replaces it, and the loop closes at injection, not at review.

## The finding that caused this

Reviewer findings used to be **prose**. The gate's blind-spot list names what no tool checks, but not
the class that *does* have a written rule and is broken anyway — server state in a composable ref
where the project uses a store, an error shape ignoring the provider layer's convention, a threshold
in prose (which invariant 13 forbids). Those appeared as reviewer prose, and **prose findings meant
nothing countable**: the write-back in `skills/harness-quality-gate/SKILL.md` proposed a standards
line after repeated violations but kept no count between runs, had no notion of a rule written and
then violated anyway, and never retired anything. Nothing distinguished a rule that was
written-and-ignored from one nobody broke.

Say it plainly, the way v1.2's doc says the old `≥9` meant nothing measured: **a prose finding is an
event with no arithmetic behind it.** v1.3 retires that write-back — two mechanisms proposing into the
same file was the failure the design exists to prevent — and replaces it with typed records, a
persisted ledger, and a Refine phase that can only propose.

## The evidence spine, as shipped

```
ticket (measurable AC + risk tier)
  → PLANNING: lane manifest built; active rules matching each lane's ownership set are pasted
              into its dispatch prompt, inside an untrusted-data fence
    → lane implements (TDD → local gate → returns the metric table)
      → scheduler (full gate → risk router)
        → reviewers (derived score; findings returned as TYPED RECORDS, validated against the manifest)
          → scheduler writes docs/harness/findings/<run>.json  (roster + manifest + tier + sourceHash)
            → gate → commit trailer (incl. Adherence:) → CODE COMMIT
              → Judge (numeric wherever a number exists — Refine has no vote)
                → REFINE (reads the window, returns at most one proposal per component, writes nothing)
                  → awaiting_confirmation: code + metrics + tier + verdict + the proposal,
                    rendered as the LITERAL text that will be written
                    → operator confirms → prose lands as a SEPARATE rulebook commit
                      → next run's dispatch prompts contain the new rule
```

**Prose lands after the code commit, and that ordering is load-bearing.** `agent-os/standards/`,
`docs/review.md`, `agent-os/learned-rules.json` and `docs/harness/refine-log.md` are all inside
`sourceHash`; only `docs/harness/findings/` is excluded, and only because it is written after the gate
runs. Writing prose before the trailer stales the report and `harness-ship-evidence` refuses —
succeeding at learning would block shipping. **Do not "fix" that by widening `GATE_ARTIFACTS`**: it
would drop the rulebook out of the hash and reproduce the `**/auth/**` TOCTOU on the rulebook itself.

The loop closes at the last arrow: injection at dispatch is what makes a rule load-bearing, and what
makes it testable — a rule demonstrably in front of the model and violated anyway is a badly written
rule.

## New invariants (16–24), each with the thing that enforces it

16. **A project's ledger is local.** It never references another project. Cross-project promotion is a
    proposal to the global templates, applied by the operator by hand.
    **Enforcer:** `harness-findings.mjs --validate-ledger` refuses any `target` outside
    `ledger.targets_allowed` (default `agent-os/standards/`); the promotion half has no code path.
17. **The Refiner writes nothing.** Data is written by the single writer that already writes the gate
    report and the commit; prose reaches a file only after the operator confirms.
    **Enforcer:** the `refiner` permission block in `opencode.jsonc` — `edit`/`bash`/`task`/
    `external_directory`/`webfetch` all `deny`. `task: deny` is what stops it delegating a write to a
    write-capable subagent. Live check C12 not yet run.
18. **Refine has no vote.** Checkable form: the Judge's dispatch payload contains no Refine output.
    **Enforcer:** dispatch contract in `skills/prevc-workflow/SKILL.md` and
    `skills/harness-refine/SKILL.md` — procedural, no code check exists. Live check C6 not yet run.
19. **A machine-learned rule is structurally incapable of blocking.** Prose rules are excluded from
    every blocking row by the adapter, not by a sentence in this file.
    **Enforcer:** `ENFORCED_ENFORCEMENTS` routing and the `rule_violations_prose` pin in
    `scripts/harness-quality-adapters.mjs`; fixtures A14/A15 plus the D21 ledger tests.
20. **Adherence is a floor, not a rate.** A count with no recall estimate beside it must be reported
    as a floor.
    **Enforcer:** `recallAnnotation`/`hasRecallAnnotation` in the adapter (fixture A17 fails if a count
    loses its annotation); `renderTable` prints the recall detail on PASS rows that carry it (T07-R1),
    unrelated PASS rows stay compact.
21. **The ledger is a working set.** The per-target cap forces a retirement; a rule with no citation
    inside its window is retired.
    **Enforcer:** procedure in `skills/harness-refine/SKILL.md` (the only mechanism that removes
    anything), with the governing numbers range-checked by `harness-findings.mjs` (exit 2 out of
    range).
22. **Prose lands after the commit.** The rulebook stays inside `sourceHash`; only the findings
    directory is excluded, and only because it is written after the gate runs.
    **Enforcer:** `GATE_ARTIFACTS = [REPORT_DIR, REVIEW_DIR, DECISIONS_PATH, FINDINGS_DIR]` in
    `harness-quality-core.mjs` plus `harness-ship-evidence` refusing on a stale report; fixture
    "sourceHash — findings writes are invisible, standards writes are not".
23. **Governing numbers live in the fingerprinted file.** A knob outside `configFingerprint`'s reach
    is a control that can be disabled with no record.
    **Enforcer:** the `learned_rules` top-level key in `agent-os/quality-thresholds.json` lands in the
    fingerprint's `other` bucket (any change needs a dated decision) and every knob has a range row in
    `harness-findings.mjs` — a knob with no row is exit 2.
24. **The operator approves text they were shown — for any rule that can block.** The confirmation
    renders the literal string, target, anchor, source findings and `refuted_by`. **Amended by D21:**
    a prose-`observe` rule, which invariant 19 already forbids from blocking, auto-activates after a
    distinct top-tier `rule-verifier` fails to refute it, and is surfaced in `refine-log.md` for veto
    on the next-run `high_risk_path` read. The operator gate is mandatory only for enforcement
    promotions and rules targeting an effect-level `high_risk_path`. **Amended by FINAL-R1
    (2026-08-12):** the storage path is not a veto trigger — every permitted target lives under
    `agent-os/standards/`, which matches the `**/standards/**` storage glob, so rejecting on it made
    verifier approval structurally impossible. Storage-path high risk is the **next-run** veto (tier
    `full` forces the human read); only a match against an effect-level glob outside the storage
    scope keeps the pre-commit operator gate. And the `auto_activate_prose_observe` knob now ships
    **false** in the template: a project opts in per-project (dated decision) after live acceptance
    C16 and an OpenCode restart.
    **Enforcer:** procedure in `skills/harness-refine/SKILL.md` (C9, not yet run); the D21 amendment is
    enforced by `--validate-ledger`: `approved_by: "rule-verifier"` requires `enforcement: "prose"` and
    a recorded `verifier_report`, and the target high-risk check is scoped to effect-level globs
    (`STORAGE_HIGH_RISK_GLOBS` in `harness-findings.mjs`).

And the one that outranks them, inherited unchanged:

> **The gate fails closed.** A missing ledger, an unparsable findings file, a window with no reviewer
> roster, or a Refine phase that could not run are gaps to name — never a pass, and never a reason to
> lower a tier. Enforcer: `readWindow`/`assessWindow` in `harness-findings.mjs` plus the tier presence
> cross-check (fixtures A5/A6).

## Practical routing for lanes (v1.3 behavior)

Workflow-level dispatch guidance (the nine cases: one-file task, small bug fix, complex feature,
independent parallel lanes, dependent serialized lanes, multi-session, high-risk/security,
documentation-only, and the Refine/learned-rule cycle) lives in `harnessopencode.md` §9.5. What
this document adds are the v1.3-specific behaviors a lane or scheduler must honor when one of those
cases lands here:

| Case | v1.3-specific behavior |
|---|---|
| one-file task / small bug fix | nothing extra: no Refine input unless a reviewer cites a rule in a typed record |
| complex feature / parallel / dependent lanes | findings are typed records, not prose; the scheduler is the single writer for `docs/harness/findings/<run>.json` — one writer per file extends to the findings directory |
| multi-session | the ledger and findings survive across sessions in the repo; nothing else v1.3-specific |
| high-risk / security | a Refine proposal targeting an effect-level `high_risk_path` keeps the pre-commit operator gate; storage-path high risk is a next-run veto, never a verifier rejection (FINAL-R1) |
| documentation-only | `--check-sources` scans `docs/harness/` — a doc line declaring a numeric threshold is a finding; docs are inside `sourceHash`, so rule prose written into docs still respects the after-commit ordering |
| Refine / learned-rule cycle | findings window → refiner (read-only, at most one proposal per component) → literal text at `awaiting_confirmation` → operator approval for rules that can block → separate rulebook commit; prose-`observe` candidates need the distinct top-tier `rule-verifier`, and auto-activation is OFF (`auto_activate_prose_observe: false`) — no live acceptance (table C, C1–C16) has run, so do not claim it |

Common v1.3 mistakes worth calling out in reviews:

- **Editing `agent-os/learned-rules.json` or `agent-os/standards/` from a code lane.** The rulebook
  is inside `sourceHash`; prose lands after the code commit as a separate commit, or
  `harness-ship-evidence` refuses.
- **Treating a rendered Refine proposal as approved.** Rendering is the confirmation prompt, not
  the approval; only the operator's confirmation writes prose (invariant 17).
- **Running the refiner on the cheapest tier.** The cost of that mistake is the layer, not the
  model (reported in the source paper; stated above).
- **Assuming the D21 auto-activation path is live.** The template ships `false`; enabling it is a
  per-project dated decision after live acceptance C16 and an OpenCode restart.
- **Widening `GATE_ARTIFACTS` to "fix" the prose-after-commit ordering.** It would drop the
  rulebook out of the hash and reproduce the `**/auth/**` TOCTOU on the rulebook itself
  (invariant 22).

## Gotchas / honest caveats

- **Adherence is a floor, not a rate.** It counts detected violations, not real ones; a degraded
  reviewer producing fewer findings reads as progress. Every violation-derived reading carries the
  recall estimate or the statement that it is absent (invariant 20), and since T07-R1 the report
  renderer prints the annotation on PASS rows that carry it — unrelated PASS rows stay compact.
- **Classification stays model-judged.** The script validates the pointer and does the arithmetic; a
  reviewer labelling a preference as a `rule_violation` with a *plausible* pointer still inflates the
  count.
- **A permanently-prose rule is a legitimate outcome, not a backlog.** Judgement rules are marked
  `prose_permanent` and the adapter filters them out of `enforced_fraction`'s denominator
  **structurally** — that exclusion is what stops the metric from pressuring people to mechanise the
  unmechanisable.
- **The loop depends on the operator approving** (the rules that can block), and D21 narrowed but did
  not remove that dependency. The design has no answer for an operator who stops approving.
- **Mid-run intervention is not delivered.** The operator asked to stop mid-plan when the work goes
  wrong. What exists is the autonomous-run halt list, `cancel_task` per lane, and the serial fallback;
  `Ctrl+C` does not kill background children. Separate work, declared rather than pretended.
- **The first occurrence of a mistake reaches nobody.** It is threshold-gated by design; the first N
  breaks are candidate evidence only. A `blind_spot` recurring within one run is surfaced as an
  observation, which is partial mitigation, not a fix.
- **The Refiner must not run on the cheapest tier.** Reported below the capability threshold in the
  source paper. The cost of that mistake is the layer, not the model.
- **Attribution is per capability, not per model** — eighteen of twenty-one agents run the same model,
  so grouping by model has one bucket.
- **What the build taught (2026-08-12), none of it papered over; round-1 repairs (T02-R1/T07-R1/T10-R1)
  closed three of the five:**
  - the nine adherence rows were not declared in this repo's runtime
    `agent-os/quality-thresholds.json#metrics` — the **template** declared all nine (T07-R1) and the
    runtime file was intentionally unchanged, so this repo's gate tables showed none of them until the
    operator opted in. **Closed by SEC-R3 (2026-08-12):** the live runtime file now declares all nine
    rows, the `learned_rules` knob block (guarded, dated entry in `quality-decisions.md`), and the
    rulebook `high_risk_paths`, with `auto_activate_prose_observe: false` — the D21 auto-activation
    toggle is **installed but off** pending restart and live acceptance (table C); with it off, prose
    candidates route to the operator path;
  - `renderTable` used to drop PASS-row detail — closed (above, invariant 20; T07-R1);
  - the symlink fixture is `# SKIP` on Windows without developer mode — the A10 symlink half is
    unverified on this machine;
  - `opencode.jsonc` changes need an OpenCode restart — the new permission blocks were not live during
    the lane run that shipped them (T05);
  - the calibration-side seam (F4: calibration owns thresholds and `AGENTS.md`; the refine loop owns
    the ledger and `standards/*.md`) was declared but `skills/harness-project-calibration/SKILL.md` sat
    outside every declared ownership set — closed by T10-R1: the skill now declares the seam.
- **No live model acceptance has run.** Verification table C (C1–C16) is model work and has not been
  executed: no injection has reached a lane, no findings file has been written by a real run, no
  sampling roster has produced the liveness numbers, and no operator has seen a rendered proposal.
  Everything that needs a model run is unverified by design — and stage 1 has nothing to measure until
  it does.
- **T07 landed after one bounded repair** — the adapter's first pass was returned and fixed within the
  lane; treat that as normal, not as evidence the shape is settled.
- **The same failure direction is assumed live in whatever is added next.** It recurred twice — five
  times during v1.2's construction, and five of the eight security blockers in v1.3's round 1 were the
  same shape: verification closed at one layer, open at the layer beneath. If you add a control, name
  the layer beneath it and check that too.

## How it was reviewed, and what that cost

Round 1 ran **three independent reviewers** over the plan-approval draft — `code-reviewer`
(judgement-only: no gate report exists for a markdown change, and it verified the hash mismatch rather
than assuming it), `security-analyst` (8 blockers), `requirements-interrogator` — producing **29
findings, all accepted**, with dispositions in the spec folder's `review-findings.md`.

The number that matters more than the count: **five of the eight security blockers were the same
shape** — a control verified at one layer and open at the layer beneath. The ledger inside the source
hash but outside the config guard. Invariant 19 written but not enforced. The reviewer's `edit` denied
but not its `bash`. The findings file bound by filename instead of by content. The source hash
defended for the thresholds file and then deadlocked by the rulebook write. `v1.2-context.md` predicted
exactly this about anything added to the system — it was right twice, and this layer reproduced the
pattern immediately. **Assume it is still live in whatever is added next.**

The cost is not recoverable retroactively: five of those eight blockers were only visible because an
external reviewer ran against the draft with the disposition "verified" written only where a command
confirmed it. The same discipline is why this document states what was run and what was not.
